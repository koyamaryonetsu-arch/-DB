# 稟議資料（ドラフト）: シネマPJ 案件対応 自動化システム

作成日: 2026-06-15 ／ 起案: 小山　／ 対象: シネマPJ（TOHO他 シネコン設備保守）

## 1. 目的・背景
シネコン設備の修理依頼はメールで不定期に届く。現状は受付・案件登録・対応方針の判断・
パートナー手配・客先日程連絡・進捗反映を人手で行っており、初動の遅れと属人化が課題。
本システムは受信メールを起点に登録〜通知〜対応検討〜文面作成〜進捗反映までを自動化し、
**「誰が・何を・どう動くか」を即時に可視化**する。AIは過去事例と人の修正から学習し、判断品質を継続向上させる。

## 2. やること（①〜⑤）と実現策

| # | やること | 実現策（何が・どう動くか） | 使う技術 |
|---|---|---|---|
| ① | メール受信 → 案件管理に登録 | 依頼メールをGmailラベル「案件登録」で拾い、AIが劇場・内容・担当・受付日を抽出してNotion案件DBに自動作成 | Gmail + Claude(Haiku) + Notion API |
| ② | メール受信 → LINEで案件通知 | 登録された案件を検知し、初期対応診断（緊急度・まず誰に相談・次の一手）を付けてシネマPJ LINEグループへ自動push | Notion + Claude(Sonnet) + LINE Messaging API |
| ③ | 対応方法をAIが検討→承認/再考→**学習** | 過去案件＋対応ナレッジを検索（RAG）してClaudeが対応方針を提案。LINEで「承認/修正」。修正内容はナレッジDBに蓄積し次回以降に反映（=学習） | Claude(Sonnet/Opus) + Voyage埋め込み + Notion(ナレッジDB) + LINE |
| ④ | パートナー先への依頼文を作成 | 案件＋確定した対応方針＋パートナー情報からClaudeが依頼メール文面を作成し、Gmail下書きに保存（人が確認して送信） | Claude(Sonnet) + Gmail下書き |
| ⑤ | 客先へ調査日/修理日を連絡→内容・日程を案件へ反映 | Claudeが客先向け日程連絡メールを下書き作成。送信/返信スレッドから日程を抽出し、Notion案件の訪問日・作業完了日・進捗を自動更新 | Claude(Sonnet) + Gmail + Notion API |

> 外部（客先・パートナー）宛メールは**自動送信せず必ず下書き承認**を既定とする（誤送信リスク回避）。
> 社内向け（LINE通知・Notion更新）は自動。

## 3. ③ AI対応検討と「学習」の仕組み（重要）

「間違ったら答えを教えると学習して正答に近づく」を、**モデル再学習ではなくRAG＋事例蓄積**で実現する
（こちらが即時・低コスト・監査可能で実務に最適。Claudeの追加学習＝ファインチューニングは不要）。

1. **ナレッジDB（Notion）**: `症状/設備/劇場 → 正しい対応 / 注意点 / 担当 / 推奨パートナー` を蓄積。初期は過去の案件DB・議事録・ドライブ資料から投入。
2. **検索（RAG）**: 新規案件が来たら、関連する過去事例とナレッジを埋め込み検索で上位抽出し、Claudeに文脈として渡して対応方針を提案させる。
3. **承認ループ**: 提案をLINEに「✅承認 / ✏️修正」で提示。
   - 承認 → ④へ進む。
   - 修正（正しい対応を返信）→ その場でやり直し＋**ナレッジDBに正解として追記**。次の類似案件で必ず参照される＝学習。
4. 効果: 使うほど正答率が上がる。誰が何を直したか履歴が残り、判断根拠も追跡できる。

## 4. システム構成図

```
[Gmail 依頼メール]──①抽出──▶[Notion 案件DB]──②検知──▶[LINEグループ 通知＋診断]
                                   │                         │
                                   ▼③ RAG検索                 │承認/修正
                        [Notion ナレッジDB]◀──学習(修正を蓄積)─┘
                                   │承認後
                                   ▼④                         ⑤
                        [Gmail パートナー依頼 下書き]   [Gmail 客先日程連絡 下書き]
                                                              │送信/返信から日程抽出
                                                              ▼
                                                   [Notion 案件DB に日程・進捗 反映]

実行基盤: Google Apps Script（無料）または Cloud Run（小規模・低額）。AI: Claude API。
```

## 6. 推奨構成と段階導入
- **Phase 1（即時・低コスト）**: ①②をGASで稼働（メール→登録→LINE通知）。基盤¥0、LINEのみ。
- **Phase 2**: ③ 対応検討＋承認＋ナレッジ学習を追加。
- **Phase 3**: ④⑤ パートナー依頼文・客先日程連絡（下書き）と案件への日程反映を追加。
- 複雑化したら基盤をGAS→Cloud Runへ移設（低額）。各Phaseで効果検証してから次へ。

## 6-2. 実行基盤の選び方（GAS と Cloud Run の違い）

| 観点 | GAS（Google Apps Script）| Cloud Run |
|---|---|---|
| たとえ | 軽自動車（近所向け・維持費0）| バン（積載・長距離OK・少し維持費）|
| 費用 | **¥0** | 月 **¥0〜3,000**（使った分だけ）|
| 1回の処理時間 | **最大6分**（重いRAG＋多数AI呼び出しは超過リスク）| 実質制限なし（長い処理OK）|
| 件数・同時処理 | 無料枠の上限あり。大量同時は苦手 | スケールする |
| 本格RAG/ログ/テスト/保守 | やりにくい・大規模化で辛い | やりやすい |
| 構築の重さ | 軽い・すぐ動く | 初期構築が重い |
| 向く用途 | **①②（軽い・即時）** | **③〜⑤（RAG・学習・承認・下書き＝重い）** |

**方針**: ①②はGAS（¥0・即時）、③を作る段で③〜⑤をCloud Runへ移設。初期費¥0・リスク最小で、
重くなってから引っ越す。最初から全部Cloud Runでも可だが初期構築が重くなるだけで月額はほぼ不変。

## 7. リスク・運用方針
- 外部宛メールは**下書き承認制**（自動送信しない）。
- 案件登録はAIが「依頼か否か」を判定し、確信が低いものは「要確認」ラベルで人へ。
- 秘密情報（トークン/APIキー）は実行基盤の安全な設定領域に保管、リポジトリに置かない。
- LINEの通数・API費は管理画面で毎月モニタリング。

## 8. 決定事項（確定）
- 想定規模: **月200件**（合計 約¥9,000/月）。
- 外部宛メール（④⑤）: **下書き→人が承認送信**（自動送信しない）。
- 実行基盤: **Phase1=GAS（無料）で開始 → ③着手時に③〜⑤をCloud Runへ移設**。
